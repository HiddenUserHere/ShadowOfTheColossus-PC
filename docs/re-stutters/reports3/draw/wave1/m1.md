## 2. Design

### 2.1 Incremental ring changes (item 1)

`HostAddOnly` runs for every `HostMaintain` change in mode 2 (group off):

1. Removal check: every applied range must lie inside one range of the new set (`ArenaBlocks`, which
   already merges the arena blocks and the heap runs). If one does not, return false (counter `removal`):
   the full path runs, with its marks for pages that leave the ring.
2. `added` = new ranges that are not exactly in `applied`. Empty means the same set: return true.
3. Import each added range with `ImportGuestRange`. Any refusal returns false (counter `refused`): the
   full path imports what it can. Nothing was applied before that point, except idempotent imports.
4. `applied = want`, `RegionManager::ring_enabled = true`, `cache.PcHostAddRing(added)` (snippet, section 5):
   `pc_host_blocks` gets the added ranges, dropping the old entries they cover, and
   `memory_tracker->AddRingRange` runs per added range (SetRingRange: per-page, same transitions as
   SetRingMask, so the ring state equals a full apply over the same pages).
5. Every 64 add-path changes a full `PcHostApply(applied)` runs (counter `periodic`). This matters because
   `AddRingRange` only touches regions that already exist (`IteratePages`): a region created later gets
   its ring bits at the next full apply. Until then it is tracked normally (correct, more write faults).

Why the old imports are not walked: `ImportGuestRange` on an already imported range is a `FindRun`
(one map lookup). The added ranges that extend an old run replace that run's key (`ImportRun` replaces by
key), which is what the full path also does.

### 2.2 Coarser units and the import cap (items 2 and 3 of the brief, serving side)

`CollectCoarseRuns` (mode 2 only), per heap:

- Walk `CollectHostGranules` in address order. A segment is a stretch of `clean` granules with no hole.
  Its `bound` granules are the anchors.
- Two consecutive anchors in one segment become one run, the unbound clean granules between them included,
  unless `cache.IsRegionGpuModified(gap)` is true (then the run is cut). Gap granules are tiled and clean,
  so they are the heap's own memory. Joins are counted.
- Each run with a GPU bit (`IsRegionGpuModified(run)`) is left out (counter `GPU-modified left out`).
- At most 64 runs are served (largest by bytes); the rest keep the normal path. Counter `capped`.
- `SetHostExtras` publishes the list (unchanged call; it bumps the block version).

No gap size limit (the brief asked for "the gap's granules are of the same heap and never GPU-written").
A gap granule is served only as ringed memory: a bind that reaches it is served from host memory, and a
normal-path bind over ringed bytes still gets the CPU marks (`PcHostMarkCpu`), so it is uploaded.

Mode 1 (`CollectHeapRuns` loop, `CollectHostServe`) still produces 64 KiB-granule runs with a 1024 cap.

### 2.3 Cheaper source than the memtype probe (item 3): investigation, not implemented

Findings from reading the code (verified in code, not measured):

- The heap runs need two per-granule facts: "claimed in heap X" (memtype `MEMTYPE_ALLOC` post, probe_memtype.cpp
  `NoteAllocGranules`, needs `SOTC_HOOK_MEMTYPE_PROBE=1 SOTC_MEMTYPE_CLASSES=1`) and "bound by the GPU" plus
  "clean" (`g_gr_bound`, `g_gr_excluded`, both set only when `SOTC_CLASS_TRACK != 0`: `NoteGpuBind` and the
  sampling feed `NoteGranuleGpuPages` are no-ops with `Mode() == 0`).
- The allocator probe (probe_alloc.cpp, `SOTC_HOOK_ALLOC_PROBE=1`, already required by ring8) sees every
  CPUMemory block with its pool name (`OnAlloc`, cpu_only = kind 1, not staging). But `OnAlloc` and
  `OnAllocOwner` store only when `SOTC_CLASS_TRACK != 0`. So a CPUMemory-block source would need
  `SOTC_CLASS_TRACK=2` but not the memtype hook. Its limitations: blocks are allocations, not heap regions
  (they would need the same gap merge), and "bound" would be per block (a bind inside a block), so
  `NoteGpuBind` would need a block-level bit.
- The class-track cost is not split in the 1 Nov measurement (3 FPS for memtype + classes + track 2 together).
  The sampling feed (`SynchronizeDmaBuffers`, 512 granules per 250 ms) is only needed for "clean"; a served
  run also checks `IsRegionGpuModified` at each collect, so "clean" is a second safety net, not the only one.
  A bind-only class mode (bound bits, no sampling feed) is a candidate, but it changes buffer_cache.cpp
  (not owned) and was not run.

Recommendation: measure before building the alloc-block source. Run mode 2 with the current memtype switches
(baseline), then the same with the sampling feed removed (needs a buffer_cache.cpp change in the snippet
owner's area). Only if the class-track share is the bulk of the 3 FPS does the block source pay.

### 2.4 Item 4: SotcLabels::NoteSharedTouch

Not used. This component does not call `SotcLabels::NoteSharedTouch` and does not include
`gpu/sotc/label_honest.h`, so it does not depend on l1's header. The label side (HostWriteSeq, deferred EOP
labels) is unchanged. Note for l1: mode 2 serves unbound clean gap granules too. Those are never GPU-written
through a served bind until they are bound, and a bind into them after serving goes through `PcHostBind` (so
it is counted by `NoteHostBind`, written binds advance `HostWriteSeq`). A straddling bind over a served gap
granule takes the normal path and sets GPU bits; the next collect then drops the run (removal path).

## 3. Counters and what they mean

5 s report, host block (`SOTC PC RING host heaps (mode 2)`, printed only in mode 2):

- `runs N (M MiB)`: served heap runs after the last collect (gauge).
- `GPU-modified left out K`: candidate runs dropped because the tracker holds a GPU bit (gauge, last collect).
- `gap joins J`: gaps joined into a run, this window.
- `capped C`: runs dropped by the 64-run cap, this window.
- `add-only ringed R runs (X MiB)`: ranges ringed by the incremental path, this window.
- `full re-applies removal A, refused B, periodic P`: full path taken, by reason, this window. A high `removal`
  count means the run set keeps shrinking (GPU writes or exclusions); `refused` means `ImportGuestRange` failed.

Stderr, once per collect (first 32): `SOTC PC RING8 heaps (mode 2): ...`. Once per add (first 8): `SOTC PC RING8 host add: ...`.

```cpp
// sotc: SOTC_PC_RING8_HEAPS_MODE=2 (pc_ring_copy.cpp HostAddOnly). The caller imported the added ranges and set
// RegionManager::ring_enabled. An entry that an added range covers is dropped from pc_host_blocks (its pages
// are in the new range). AddRingRange is the per-page incremental form (SetRingRange), no whole-region apply.
void BufferCache::PcHostAddRing(const std::vector<SotcPcRing::RingExtent>& added) {
    {
        std::scoped_lock lock{pc_host_mutex};
        std::erase_if(pc_host_blocks, [&added](const SotcPcRing::RingExtent& old) {
            return std::any_of(added.begin(), added.end(), [&old](const SotcPcRing::RingExtent& a) {
                return old.addr >= a.addr && old.addr + old.size <= a.addr + a.size;
            });
        });
        pc_host_blocks.insert(pc_host_blocks.end(), added.begin(), added.end());
    }
    for (const auto& range : added) {
        memory_tracker->AddRingRange(range.addr, range.size);
    }
}
```

Includes needed in buffer_cache.cpp: `<algorithm>` (std::any_of) and `<vector>`. Both are almost certainly present
(std::sort is used in the same file); check when applying.

## 6. Risks

- Stale ring state for regions created after an add: covered only by the periodic full apply (every 64 adds).
  Failure mode is more write faults, not stale data (a region without ring bits is tracked normally).
- Gap joins serve unbound granules. Correct under the existing rules (a served bind is host-backed, a normal
  bind over ringed bytes is marked), but it widens the set of pages whose CPU writes are not seen. Only CPU
  writes to pages the GPU never binds are affected, and those are never read by the GPU through a served bind
  without an earlier collect.
- Import refusal in the add path falls back to the full path each change while the refusal lasts (no retry
  cache in the add path). In the full path refused ranges are not retried. Expected to be rare.
- The 64-run cap drops the smallest runs (by size, dropped ones keep the normal path). A dropped run that
  was already served becomes a removal (full path, marks).
- `AddRingRange` is untested in mode 8 (mode 5 uses it for hot pages only).
- Not tested in game. Nothing was built or run, so every behaviour above is from reading the code.
