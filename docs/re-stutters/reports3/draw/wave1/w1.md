# W1: resolve workers on generation sums (SOTC_PR_GEN)

Status: code written and syntax-checked only. Not built with ninja, not run in the game (per the wave
rules). The real `video_core/sotc_generation.h` does not exist yet; the check used a scratch stub
(`SotcGen::On/Sum` returning constants) and `-fsyntax-only` with the exact `compile_commands.json`
flags, plus `-Wall -Wextra` on the edited ranges: no errors, no warnings. `liverpool.cpp` (includes
`draw_prep.h`) also compiles clean.

## What changed

Files: `gpu/shadps4/video_core/amdgpu/draw_prep.h`, `gpu/shadps4/video_core/renderer_vulkan/vk_rasterizer.cpp`.

- `draw_prep.h`
  - `PrBuffer::gen_sum`: `SotcGen::Sum(base, vsize)`, read before the mapping read.
  - `PrImage::gen_sum`: `SotcGen::Sum(address, 1)`, read before the mapping check.
  - `PreparedResources` static_assert bound moved from 4 KB to 8 KB (the sums add 8 bytes per descriptor).
- `vk_rasterizer.cpp`
  - `#include "video_core/sotc_generation.h"`.
  - `SotcPrGenMode()`: reads `SOTC_PR_GEN` once. Returns 0, 1 or 2. Refused (0, with a stderr line) when
    the value is above 2 or `SotcGen::On()` is false. The API is only queried when the variable is set.
  - `kPrGenMaxSpan` = 64 MiB: a buffer longer than this is not prepared (`computed` stays false, the
    owner resolves it inline). Keeps the owner's sum walk bounded.
  - `PrResolveBuffer`: with the mode on, takes the sum before `ClampRangeSize`.
  - `PrResolveImage`: with the mode on, takes the sum before `IsValidGpuMapping` (verdicts 0 and 2 do not
    read the mapping and take no sum).
  - `PrGenSumsUnchanged()`: the owner-side test. Recomputes `Sum` for every computed buffer and every
    verdict-1/3 image of the prepared draw, and compares with the recorded sums.
  - `PrGenNote()` and `g_pr_gen`: the counters, owner thread only, printed every 5 s.
  - `BindResources`: the gate. With the mode on, the prepared values are used only if the table
    generation still matches (kept, conservative) and every recorded sum still matches. Otherwise the
    draw resolves inline (needs-owner). Mode 2 runs the owner's computation (`PrepareResources` on the
    owner) and compares it with the prepared values when the sums are unchanged; the owner's values are
    used.
  - `PrepareDraw`: resolves on the prep thread when `SOTC_PR_RESOLVE` or `SOTC_PR_GEN` is on.

Nothing else changed. With the mode unset, the existing `SOTC_PR_RESOLVE` decision is the same as before:
`resolved` is set exactly when the table generation matches.

## Switch

`SOTC_PR_GEN` (default unset = 0; needs `SOTC_PARALLEL_RECORD=1`; needs the generation API on)

| value | behaviour |
|---|---|
| unset / 0 | off, as before |
| 1 | prepared resource values used while the table generation and every range sum match; otherwise inline |
| 2 | same gate as 1, but the owner always resolves inline; when the sums matched, the prepared values are compared with the owner's computation and disagreements are counted |

`SOTC_PR_GEN` works without `SOTC_PR_RESOLVE` (it enables the resolve step by itself).

## Counters (stderr, every 5 s, printed from BindResources while the mode is on)

Line: `SOTC PR GEN (mode N): prepared hits H, needs-owner O (table generation T), verify mismatches M`

- `hits`: draws whose prepared resource values passed the gate. In mode 2 this counts draws whose
  sums matched (the values are then compared, not used).
- `needs-owner`: draws resolved inline because the table generation moved (`T` of them) or a recorded
  sum no longer matches.
- `verify mismatches`: mode 2 only. Sums matched but the prepared values differ from the owner's
  computation. Must be 0. The first 16 are also logged as `SOTC PR GEN verify mismatch`.

No call-site snippet is needed: the report lives in `vk_rasterizer.cpp`.

## Ordering and correctness argument (assumes the generation API contract)

- Worker: sum read first, then the mapping read. If a change lands after the sum read, the owner's sum
  differs and the draw goes inline.
- Owner: sums recomputed at bind time over the same arguments.
- The argument needs the API to satisfy: (a) a mapping change (map AND unmap) bumps the granules it
  touches, (b) the bump happens after the change is visible, (c) `Sum` reads are acquire, and the
  worker's sum read is ordered before its mapping read. Item (a) matters: the design text lists unmap
  only, but a new mapping also changes `ClampRangeSize` and `IsValidGpuMapping`.
- The prepared values depend only on mappings (and the V#/T# words, which come from the op's captured
  flat copy), not on memory contents. So content writes need no bump for this component.

## Ranges and what was NOT covered

- Covered: buffer `[base, base+vsize)` (V#), image granule at T#.address.
- Not covered, by design of this component:
  - The bind memo key (`FastBindHash`) and `BindResourceHash` are computed on the worker from registers
    and sharps only (no memory read), so no sum is recorded for them. Their validity is still the
    owner's existing generation check (`CommitFastBind`, `fast_bind.*_generation`).
  - The pipeline key is not resolved by the worker in this code (`op.pipeline` comes from the command
    processor, `LookupGraphicsPipeline`). No pipeline range sum exists. Shader code ranges are not
    checked by this change; if the code can be remapped under a live pipeline, that is a gap.
  - DMA pointers, sharp tables, fmasks, storage images and array descriptors are still not resolved
    on the worker (`PrStageResolvable`, unchanged).

## Memory

`PreparedDraw` grows by about 768 bytes (48 buffers + 48 images, one u64 each), so the prep ring
(512 slots) grows by about 0.4 MB. Estimated from field sizes, not measured.

## Risks

1. Correctness depends on the generation API's bump contract above (map and unmap, ordering). A missed
   bump is a silent stale mapping (wrong buffer size or a wrong texture verdict). Mode 2 is the only check.
2. The table-generation gate stays (conservative). If the runtime table generation moves often, the
   `table generation` part of needs-owner stays high and PR_GEN gains little. The counter shows it.
3. `TakePrepared`'s epoch test (above) can dominate needs-owner in practice.
4. `kPrGenMaxSpan` sends very large descriptors inline. Unused bindings often carry garbage descriptors
   with huge sizes (see the comment in `BindBuffers`), so they will show up as inline work.
5. Cost: one extra `Sum` per buffer and image in PrepareResources (worker), and one `Sum` per recorded
   range per prepared draw in BindResources (owner). Not measured. The owner pays for the sums on every
   prepared draw, so the gain depends on `Sum` being much cheaper than `ClampRangeSize`.

## How to test (once the API and `sotc_generation.h` exist)

1. Build as usual (`bash build.sh`), then run the Lab route with the usual matrix config plus
   `SOTC_PARALLEL_RECORD=1 SOTC_FPS=1` and the generation API switch that the generation agent defines.
   Needs more than 6 hardware threads.
2. First `SOTC_PR_GEN=2`: `verify mismatches` must stay 0 for the whole run. Any non-zero value is a
   bump contract bug, not a tuning issue.
3. Then `SOTC_PR_GEN=1`: compare `needs-owner` with `table generation` and with the existing `pr_epoch`
   count (FPS log); compare the draw-thread median against `SOTC_PR_GEN` unset (A/B, same route).
