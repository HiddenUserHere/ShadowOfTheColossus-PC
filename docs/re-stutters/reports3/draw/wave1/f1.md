## The switch

- `SOTC_FLIP_OFFTHREAD=1` turns it on. Unset or any other value is off (the default).
- With it off, `ready_queue` stays empty, `RefillReadyFrames` returns at once, and `GetRenderFrame` takes the
  same frame it took before. The only code difference with it off is the wait predicate
  (`free || ready`), which is equivalent when `ready` is empty.

## Counters (SOTC_FPS=1, per 5 s)

- `SOTC FLIP WAIT` (existing line, unchanged): `no free frame` ms per frame and `present_done fence` ms per frame.
  These are the draw-thread wait "before/after" numbers. Compare a run with the switch off and one with it on.
- `SOTC FLIP OFFTHREAD (<s>, on|off)` (new line):
  - `frames handed off to ready`: `RefillReadyFrames` moves (present thread).
  - `frame requests served from ready of N`: `GetRenderFrame` calls that took a ready frame (from any thread;
    blank frames on the present thread can take one too).
  - `frames dropped`: must be 0. It counts only the RecreateFrame-failure path (a frame not given back).

## Ordering argument (for the comments in the code)

- The copy of the VO buffer into the frame is still recorded by the draw thread inside `PrepareFrame`, at the
  same place in its stream as before. Only the choice of frame changes, and the frame's `present_done` fence is
  still waited on in `GetRenderFrame` (it returns at once for a ready frame, since the refill checked it).
- The early VO label release (`SubmitFlipInternal`, `EarlyVoLabel`) is still after `PrepareFrame`, so the
  CP's wait on the label is exactly as before.
- Presents still go out in request order; the frame a flip uses is the front of the same FIFO (ready first, and
  a ready frame was the front of `free_queue`), so frame ids and presentation order do not change.
- Flip events, `flip_status`, `flip_pending_num` and the VideoOut status are all updated in the same places in
  `Flip` and `SubmitFlipInternal`; none are touched.
- A frame is in exactly one of free_queue, ready_queue, the draw thread's hand, or presenting. The
  refill and the takers all use `free_mutex`. No frame is discarded.

## Risks

- **The free-frame wait is not removed.** When every presentation frame is in use (present thread behind by
  the ring), a ready frame does not exist, and the draw thread still waits for a free frame. The handoff only moves
  the `present_done` fence wait, and the present-thread refill. Larger ring: `SOTC_PRESENT_FRAMES` (existing).
  A true "never block on a free frame" needs draw-owned capture images, which is not done here.
- The fence poll runs once per present-thread tick (about 8 ms at 120 Hz). A frame that is free may reach
  ready up to one tick late. It is never lost.
- The draw thread's fallback wait (`no ready frame`) still blocks: it is counted, not removed.
- Pre-existing, unchanged: `DrawLastFrame` (present thread) re-presents `last_submit_frame` with reuse, which
  can overlap a draw-thread copy into the same frame. The refill makes a frame ready a bit later than
  before, so this window is not larger.
- Changing the predicate of `GetRenderFrame` (`free || ready`) is only exercised with the switch on.
