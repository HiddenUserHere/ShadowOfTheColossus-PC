# The constant 40–60 ms frames and the plan for a locked 30 FPS (8 Nov 2026)

## What the stutter is

With the compile stalls gone (manifest, GPL no-drop, pack libraries), the test route still shows p99 of
42–59 ms and 2–10 frames above 50 ms per route, and the user feels a constant judder. Two causes, both
measured:

### 1. The render threads are at the budget

Per-frame CPU on the warm route (`SOTC cpu/frame`, several sessions):

| Thread | ms per frame | Role |
|---|---|---|
| `GpuCommandProcessor` (CP) | 28–30 | parses the PM4 stream, resolves pipelines, feeds the draw thread |
| `GpuDraw` (draw) | 31–34 | binds and records 3,000–6,000 draws |
| recorder | 20–23 | replays the recorded stream into Vulkan command buffers |

The budget is 33.3 ms. The draw thread is above it and the CP just below, so any heavier frame (streaming,
particles, more draws) lands at 36–45 ms. The draw thread also sleeps 10% of its time waiting for the CP
(`FutexSleep`, ~680 wake-ups per frame), so cutting only the draw thread moves the bound to the CP.

### 2. No frame pacing: a 36 ms frame is shown for 50 ms

The 30 FPS cap is a software timer at 60 Hz (`driver.cpp:3310`, `AccurateTimer`), not the display vblank.
A frame is taken only when two ticks have passed since the last flip (`driver.cpp:3482-3484`); a frame that
is not ready at its tick waits for the next one. So a 36 ms frame is displayed for 50 ms and the next one
arrives early: judder, even when the average is 30 FPS. The present mode is forced to FIFO
(`vk_swapchain.cpp:258-260`); there is no pacer. `SOTC FRAMES` measures when the present thread takes a frame,
not the display cadence; `Presenter::PresentDoneNs` (`vk_presenter.cpp:1894-1940`) has the display-side
times but nothing logs them.

## Where the draw thread's 31 ms go (profile `user/prof/gcn/draw_warm.txt`)

| Item | ms of 28 | Fix |
|---|---|---|
| Descriptor sets written and committed on every draw, even on a bind-cache hit (`DescriptorHeap::Commit`, `BindStageSets`, driver time in nvoglv64) | ~4 | keep the committed sets in the bind-cache entry and rebind them on a hit; or push descriptors |
| `SynchronizeMemoryFull` page-bitmap walks that find nothing (`changed copies 0/0`) | ~2.8 | `SOTC_SYNC_FAST=1` (2 MiB generation stamps; measured earlier: p99 66 → 58 ms on the bind matrix) |
| REPLICATE fill shader run on the CPU (~170 per frame: memcmp against guest memory, write-back) | ~2 | run the fill on the GPU, write back lazily; first step: skip the memcmp when the generation sum and pattern hash are unchanged |
| Flat constant buffers re-copied into the stream ring on every hit (~3,000 per frame, memcpy + XXH3) | ~1.4 | a persistent flat-constant arena: upload once per hash, retire by fence |
| Unprotects run synchronously on the draw thread even with `PROTECT_ASYNC` | ~0.8 | queue them when the next reader is the GPU; no watchers for GPU_ONLY regions |
| `GetSampler` mutex per sampler per draw | ~0.5 | cache the sampler handles in the bind-cache entry |
| Diagnostics (`SotcOpPhases`, `ScopeMin`, timers) | 0 | all off under LEAN; the profile credits callee samples to inlined destructors |

Total about 11.5 ms, draw thread to about 17–20 ms. The bind-cache hit rate is already 96%, but only 47% of
ops are eligible (compute, storage and fmask binds are refused): making those eligible is a further cut.

Beyond the items: a prepare thread that runs the bind-cache lookup, stamp check, flat copy and descriptor
write list one op ahead of the draw thread, validated by stamp equality (the model `SOTC_PARALLEL_RECORD`
and `SOTC_PR_RESOLVE` started but left the expensive parts inline). Full parallel recording across render
passes is possible (`SOTC_PASS_SEC` records big passes into secondaries) but the serial tracking share
(about 30%) caps the gain and the risk is high.

## Where the CP's 28 ms go

Not profiled in this pass. Known from before: the SRT walker was 100% of the "unknown waits"; the
`flattened_ud_buf.assign` per stage and the register-chunk memcpy run per op; about 800 `WakeByAddress`
calls per frame wake a draw thread that is rarely asleep. Measurement first: `SOTC_PROFILE=GpuCommandProcessor`
on the same route, then the same kind of table.

## Plan

In order of effect on what the user feels:

### A. Frame pacer (hides 25–40 ms variance)

1. Log the `PresentDoneNs` deltas beside `SOTC FRAMES` (histogram: 2 vblanks, 3 vblanks, more). This is
   the real display cadence and the gate for everything below.
2. Pacer: present the newest completed frame every 2 display vblanks, phase-locked to the last
   `PresentDone`, from a one-frame queue (the `FLIP_THREAD` + `FLIP_IMAGES` ring already exists). A frame
   that is late by less than one vblank still goes out on time from the queue. Cost: about one frame of
   latency; switch `SOTC_PACER`, off until measured.
3. Gate: on the route, frames shown for 3 vblanks go from ~70% to under 2%.

### B. Draw thread to ≤ 20 ms

The six items above, each behind a switch, measured one at a time on the route (one round each, no
warm-up): descriptor reuse on hits, `SYNC_FAST`, fill HLE on the GPU, flat-constant arena, async
unprotects, sampler cache. Then the prepare thread for the bind work.

### C. CP to ≤ 20 ms

Profile the CP on the route, then the same treatment: SRT walk plan (`SOTC_CP_PRECISE_WAIT`,
`SOTC_CP_LABEL_SKIP`), wake only when the draw thread sleeps, per-op register and flatten copies.

### D. Memory

- Bound the live driver cache: do not load a `sotc_vk_pipelines.bin` above a size cap, start fresh
  (measured: the 2 GB file cost 2.3 GB of RAM and a fresh one is 25 MB; on NVIDIA the driver's own disk
  cache served the route with 0 waits).
- Keep the pack cache read-only.
- After the first loading screen keep only what loaded materials and the manifest reference; the pack
  libraries and compute pipelines are rebuilt from the cache on demand.

### E. Compute pack (in progress)

Every compute program compiled at the first loading screen into the pack cache, so a new area's dispatch
is a cache hit instead of a 200 ms recorder wait.

## Gates for "locked 30"

- Route: draw ≤ 20 ms and CP ≤ 20 ms CPU per frame; 0 frames above 50 ms; 0 drops; 0 CP library waits.
- Display: fewer than 2% of frames shown for 3 vblanks (from the `PresentDone` histogram).
- Cold first launch: the loading screen may be long; after it, the same gates.
- Memory: under 5 GB private at the end of the loading screen, under 9 GB at the end of the route.
- The user's own cold launch, with no warm-up, feels smooth.
